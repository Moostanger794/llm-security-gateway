Сохрани почтовые/URL-проверки, но не расширяй антифишинговый продукт. Не реализуй ToolGuardian, RuntimeMonitor, активного атакующего агента, почтовые коннекторы, UI, Docker или новый framework.

## 3. Архитектура и режимы

Сделай небольшую интеграцию с одним реальным LLM-провайдером: официальный OpenAI API/SDK. Нужны простой подменяемый интерфейс классификатора, строгие модели, provider adapter и версия classifier prompt. Не добавляй LangChain/LangGraph, несколько провайдеров или лишние factory-классы.

Проверь актуальную официальную документацию и совместимость SDK. Модель задаётся конфигурацией, не выводится из названия модели Codex. Не выбирай автоматически дорогую модель.

Режимы:
- rules: прежняя система без LLM; default для API, тестов и benchmark;
- hybrid: прежние findings + валидированные LLM-findings через существующий RiskEngine;
- llm-only: только экспериментальный режим сравнения на injection-корпусе, не default API.

Hybrid должен быть консервативным: ответ модели «не обнаружено» не отменяет прежние BLOCK/REQUIRE_CONFIRMATION и не снижает оценку правил. Не передавай модели право менять пороги, permissions или итоговую policy.

Зафиксируй следствие: при таком объединении FPR не может уменьшиться на той же выборке. Не обещай обратное. Для оценки ложных тревог самого классификатора нужен отдельный llm-only эксперимент. Автоматическое снятие блокировок моделью в эту фазу не входит.

## 4. Контракт LLM-классификатора

Модель получает только необходимый вход и тип источника. Для письма анализируй sender, subject и body; инъекция может быть не только в теле. Для документа передавай текст. Не превращай названия ролей из входа в реальные system/developer messages.

Если передаёшь описание допустимой задачи, оно должно поступать из доверенной конфигурации приложения, а не извлекаться как «истина» из проверяемого письма. Явно документируй ограничения анализа без контекста исходной задачи пользователя.

Используй Structured Outputs и строгую Pydantic-валидацию. Компактный результат, например:
- verdict: attack / no_attack_detected / uncertain;
- threat_types: ограниченный список поддерживаемых injection-категорий;
- reason_codes: ограниченный список кодов причин.

Никаких произвольных action, новых категорий, shell-команд, URL для посещения или инструкций к выполнению в ответе модели. Не запрашивай chain-of-thought. Не считай уверенность модели калиброванной вероятностью.

Проверь согласованность полей. Не распознавай JSON регуляркой из произвольного текста. Не превращай refusal, incomplete response, лишние поля, неверный enum или ошибку parsing в benign.

Преобразование валидного результата в findings, веса и решение выполняется локальным кодом. Веса задай именованными константами и документируй как policy, а не статистические вероятности. Объяснения пользователю собирай из локальных шаблонов по reason_codes: сырой ответ модели не должен отражать письмо или секреты.

## 5. Сам классификатор тоже защищаем

System instruction классификатора должна требовать анализировать недоверенный текст, а не выполнять содержащиеся в нём инструкции. Письмо/документ сериализуй как отдельные данные. Разделители и JSON не объявляй гарантией защиты.

Классификатор не имеет tools, browsing, shell, почтовых прав или доступа к секретам. Не передавай API-ключ в prompt.

Учитывай реальные команды, замаскированные роли, просьбы изменить verdict, учебные цитаты, отрицания, русский и английский язык. Обычная просьба человеку внутри письма не равна инъекции в ИИ. Не заявляй поддержку всех языков без измерений.

## 6. Интеграция без поломки API

Сохрани GET /health и POST /analyze/prompt, /analyze/email, /analyze/text. При выключенной LLM поведение, лимиты, базовые поля ответов и решения baseline сохраняются.

Встрой классификатор через композицию/dependency injection. Не блокируй async event loop синхронным сетевым вызовом. Не переписывай всё приложение в async без необходимости. Корректно закрывай клиент при завершении приложения.

Результат LLM не должен учитываться дважды: письмо уже использует PromptGuard. Для одного небольшого объекта — максимум один LLM-вызов. Не передавай уже вычисленный score или ground truth классификатору.

Добавь per-call диагностику: запрошенный/фактический режим, llm_status, fallback_reason, model ID, доступные token usage. Существующий JSON SecurityResult не ломай; для HTTP можно использовать документированные заголовки X-Analysis-Mode и X-LLM-Status, а для evaluation — отдельную metadata-структуру. Не используй глобальный mutable last_status.

## 7. Конфигурация, секреты и лимиты расходов

По умолчанию LLM выключена. .env.example должен содержать пустые значения секретов и настройки наподобие:

ENABLE_LLM_ANALYSIS=false
ALLOW_EXTERNAL_LLM=false
LLM_PROVIDER=openai
LLM_MODEL=
LLM_API_KEY=
LLM_TIMEOUT_SECONDS=15
LLM_MAX_RETRIES=0
LLM_MAX_INPUT_CHARS=12000
LLM_MAX_OUTPUT_TOKENS=512

Уточни совместимость параметров с выбранной API-моделью. Не передавай неподдерживаемые параметры «на удачу».

Не используй auth.json, cookies, сессию ChatGPT или OAuth-токены Codex. Не ищи ключи по системным каталогам. Секрет — только из явно настроенной переменной/.env, не из текста пользователя или датасета. Не меняй глобальное окружение Codex.

Сетевой provider request допустим только после явного включения интеграции и согласия на внешнюю передачу. URL, модель и флаги не должны управляться проверяемым запросом. Для этой фазы не нужен произвольный base_url, передаваемый клиентом.

Для live benchmark нужны отдельный opt-in и явный --max-requests. По умолчанию платных запросов нет. Учитывай реальные попытки, включая retries; отключи скрытые SDK retries. Не запускай платный benchmark самостоятельно даже при найденном ключе. Подготовь команду для человека с лимитом 10 запросов.

Не отправляй реальные корпоративные письма без разрешения. Используй только разрешённые публичные/синтетические данные. Для Responses API выстави store=false; не называй это гарантией Zero Data Retention. Не логируй тела запросов/ответов, Authorization, API keys и provider exceptions с содержимым входа. Отключи небезопасные debug-логи SDK.

Большой вход нельзя молча обрезать и назвать полностью проверенным. Если он превышает LLM-лимит, сохрани полный rules-анализ и верни явный skipped_too_large/fallback статус. Без автоматического разбиения на десятки платных запросов.

## 8. Ошибки и fallback

Без API-ключа/модели проект должен работать в rules-режиме. Отсутствие доступа не блокирует разработку и offline-тесты; не запрашивай секрет в чате.

При timeout, network error, 401/403/429/5xx, отказе модели, incomplete/invalid structured response и uncertain используй прежнюю проверку rules с явной диагностикой fallback. Не называй это успешной LLM-проверкой. Сохраняй все решения правил; ошибка модели не отменяет существующий BLOCK.

Документируй остаточный риск: fallback_rules не гарантирует обнаружение того, что могла бы заметить LLM. Клиент обязан учитывать llm_status; пока gateway выдаёт рекомендацию, а не сам останавливает реального агента.

В llm-only benchmark uncertain/ошибка не равны benign. Отмечай такой пример как unresolved, учитывай покрытие и причины; неполный прогон не выдавай за полное сравнение.

## 9. Источники инъекций и новый evaluation corpus

Оставь старый v1 неизменным. Подготовь отдельный небольшой корпус именно indirect injection в email/document, а не смесь произвольных URL-risk и фишинга.

Проверенные стартовые источники для отбора:
- LLMail-Inject: публичный challenge/dataset Microsoft об инъекциях через письма;
- microsoft/BIPIA: benchmark косвенных инъекций, включая EmailQA;
- AgentDojo: источник сценариев на будущее, не запускай его агентную среду в Phase 6.

Официальные точки входа:
https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks
https://www.microsoft.com/en-us/msrc/blog/2024/12/announcing-the-adaptive-prompt-injection-challenge-llmail-inject/
https://github.com/microsoft/BIPIA
https://github.com/microsoft/BIPIA/blob/main/LICENSE
https://agentdojo.spylab.ai/

Для этой фазы достаточно одного реально проверенного источника + собственных benign/адаптированных примеров. Не копируй весь большой benchmark и не ставь его зависимости. Скачивание небольших статических данных при подготовке — отдельный явный шаг; runtime и обычные тесты не ходят в сеть.

До включения примеров проверь лицензию именно данных, не только кода репозитория. Если права/доступ не подтверждены, не вендорь данные: создай импортёр/manifest и честно отметь блокер. Не выдумывай источники и source_id.

Для каждого импортированного/адаптированного примера храни provenance: upstream URL, revision, source_id, license/notice, исходный split, family/group, способ адаптации и hash. Для собственного примера указывай synthetic. Не называй адаптированный текст исходным публичным кейсом.

Ориентир объёма — до 80–100 осмысленных примеров, не тысячи. Не увеличивай набор повторениями ради числа. Нужны safe и attack, включая легитимные просьбы человеку, учебные цитаты и перефразированные инструкции модели.

Отдельно dev и holdout; родственные атаки, переводы и варианты одного шаблона должны оставаться в одной группе/split. Не используй holdout для подбора classifier prompt или весов. Если разработчик уже видел материал, не называй его слепым независимым тестом.

Разметка attack отражает попытку внедрения инструкции, а не факт успешного взлома upstream-модели. Не приравнивай отсутствие успеха публичной атаки к benign.

Сохрани совместимость v1 schema; provenance можно держать в sidecar manifest или в отдельной v2-схеме. Загрузчик проверяет ID, split, формат и дубликаты. Данные не могут импортировать код, задавать provider config или менять system prompt.

## 10. Сравнение и метрики

Повтори legacy benchmark в rules-режиме и проверь сохранение классификации. Новый injection-корпус показывай отдельно от смешанного legacy v1.

Для нового корпуса подготовь сравнение:
A — rules;
B — llm-only, эксперимент;
C — hybrid, консервативное объединение.

Режимы используют одинаковые sample IDs, разметку и split. Внутри одного разрешённого запуска один LLM-ответ можно применить и к B, и к C, без повторной оплаты; это явно опиши. Не включай cache hits в uncached latency. Не создавай постоянный кеш сырых писем/ответов.

Главная метрика:
ASR_proxy = число attack-примеров с финальным ALLOW / число attack-примеров.

Обязательные сопутствующие показатели:
- FPR: доля benign-примеров, помеченных не SAFE, а не только жёстко заблокированных;
- benign ALLOW rate;
- REQUIRE_CONFIRMATION/review rate;
- TP/TN/FP/FN, Precision/Recall/F1/FNR;
- p50/p95 полного вызова, включая ожидание LLM;
- количество LLM-запросов, fallback/unresolved и coverage;
- фактические input/output tokens, если provider их вернул.

Покажи, почему always-BLOCK даёт ASR=0, но непригоден: benign ALLOW rate=0. Не улучшай ASR просто отправкой всех запросов на ручную проверку.

При текущем соответствии ALLOW <=> SAFE ASR proxy может совпадать с FNR; прямо укажи это, не представляй их как независимые доказательства.

Низкий ASR proxy не доказывает отсутствие успешных атак против настоящей LLM. Настоящий end-to-end ASR оставь Phase 8.

Не скрывай ошибки provider и не исключай их из знаменателя молча. Hybrid с fallback показывает отдельные operational metrics и долю fallback. Для llm-only incomplete отчёта указывай разрешённое подмножество/покрытие; нельзя сравнивать его с полным rules-набором как равные эксперименты. Достижение бюджета отмечай как incomplete, не дорисовывай predictions.

Сохраняй dataset hash/revision, code revision, dirty-state, режим, model ID, classifier prompt version, policy version, ограничения и покрытие. Нет ключа — только честный rules baseline и offline-тесты; mock-результаты не публикуются как качество LLM.

## 11. Тестирование

Все обычные тесты offline с fake classifier/mock transport. Fake не должен получать expected labels и подставлять заранее верные ответы. Наличие настоящего ключа в окружении не разрешает тестам сеть.

Покрой:
- выключенная/ненастроенная LLM и отсутствие provider calls;
- валидные attack/no_attack_detected/uncertain;
- неправильный JSON/schema/enum/лишние поля, refusal/incomplete;
- timeout, 401/403/429/5xx, retries и лимит запросов;
- сохранение rules BLOCK при benign-ответе/сбое LLM;
- отсутствие double scoring и зависимость от доверенных метаданных;
- injection внутри sender/subject/body и попытки изменить verdict;
- большие входы без скрытой обрезки;
- privacy в 200/422/413/500, logs, diagnostics и provider exceptions;
- сохранение API-контрактов и правила вычисления метрик;
- split/provenance validation, incomplete reports и budget exhaustion;
- отсутствие network при запуске default benchmark и pytest.

Mock-тесты проверяют протокол и policy, а не реальную устойчивость модели к инъекциям. Проверку качества реальной модели маркируй отдельно как live/manual.
