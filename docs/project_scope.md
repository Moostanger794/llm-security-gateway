# Scope after КП1: Phase 6

Исследовательский вопрос: как LLM-классификация indirect prompt injection в письмах
и внешних документах и её объединение с правилами влияют на пропуски, ложные
тревоги, задержку и фактический расход токенов?

Проект — экспериментальный дополнительный слой анализа, а не замена Guardrails AI,
универсальная security platform или гарантия защиты. Gateway рекомендует решение;
вызывающая система обязана исполнить BLOCK/REQUIRE_CONFIRMATION.

Phase 6 сохраняет API и все прежние detection rules, веса, пороги и datasets v1.
Сравнение выполняется отдельно на небольшом корпусе email/document injection:

- **rules**: прежний локальный анализ, по умолчанию без сети и ключей;
- **llm-only**: эксперимент только в evaluation; ошибка/uncertain означает unresolved;
- **hybrid**: объединение findings через прежний RiskEngine. Модель не снимает
  блокировки и не понижает риск. Следовательно, FPR на тех же примерах не может
  уменьшиться. Для собственных false positives модели нужен llm-only.

Основная метрика — ASR proxy: attack с ALLOW / все attack. Это не end-to-end ASR
реального агента. При текущем ALLOW ⇔ SAFE proxy численно совпадает с FNR, поэтому
они не являются независимыми доказательствами. Always-BLOCK даёт proxy=0, но также
benign ALLOW rate=0; review rate и FPR показываются вместе с пропусками.

MockTransport и fake classifier проверяют контракт, fallback, privacy и policy,
но не измеряют качество настоящей LLM. Доступ к API не требуется для завершения
offline-разработки. Live-вызовы выполняет человек отдельной командой с opt-in,
согласованными публичными/синтетическими данными и явным бюджетом попыток.

Не входят в Phase 6: ToolGuardian, RuntimeMonitor, исполнение атак против агента,
почтовые коннекторы, UI, Docker, новый framework, расширение антифишингового продукта.
AgentDojo остаётся источником будущих сценариев; его среда не запускается.
End-to-end проверка успешности атак относится к Phase 8. AGENTS.md сохранён;
PHASE_6_CODEX_PROMPT.md уточняет его старую дорожную карту.
